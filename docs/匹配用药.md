# 匹配用药

## 1. 文档目的

本文专门梳理：

- `ComplexMutationServiceImpl.matchComplexMutation`
- `ReportCrServiceImpl.handleDrugList`

围绕最终返回的 `List<Map> drug_var_list`，逐条说明：

1. `drug_var_list` 的组成来源
2. 每个字段是谁写进去的
3. 药物匹配规则
4. 药物等级分类规则
5. 本地库与知识库优先级
6. 相关 SQL
7. 共突变、胚系、HRD、未知临床意义等特殊逻辑

输出对象不是一个固定 Java Bean，而是一个“动态增强的 Map 集合”。同一条记录在流程中会不断被补字段。

## 4. `drug_var_list` 初始组成来源

## 4.1 癌种和父子级癌种

调用：


- `analysisReportDao.getSonDiseaseList(diseaseId)`

作用：

- 生成 `diseaseIdList`
- 生成 `parentdiseaseIdList`
- 生成 `sondiseaseIdList`

这些集合不会直接放进 `drug_var_list`，但决定后续药物匹配范围、父子级癌种优先级、临床试验过滤范围。

## 4.2 体系位点加入 `drug_var_list`

- 其他模板走 `en7` 视图

这些记录是 `drug_var_list` 的第一类来源，代表体系突变。

## 4.3 胚系位点加入 `drug_var_list`

## 5. `drug_var_list` 每条记录的字段来源

`drug_var_list` 不是一次性构造好，而是分阶段补字段。

## 5.1 第一阶段：原始来源字段

### 5.1.1 体系位点原始字段

来源：

- `getThisGeneticmarkeren7VwList` / `getThisGeneticmarkerVwList`

常见原始字段：

- `gene`
- `variant`
- `ori_variant`
- `cosmic`
- `mutFreq`
- `ExonicFunc`
- `type`
- `has_drug`
- `parent_mutID`（可能为空）

### 5.1.2 胚系位点原始字段

来源：

- `getCrAll`

常见原始字段：

- `Gene`
- `Exon`
- `cHGVS`
- `pHGVS`
- `Zygosity`
- `variant`
- `ori_variant`
- `has_drug`
- `rc_record_id`
- `check_date`

说明：

- 胚系字段原始大小写与体系位点并不完全一致
- `update_cr_info` 之后会补充统一可用字段，如 `mutDesc`、`rpCr`

### 5.1.3 共突变原始字段

来源：

- `getComplexMutationById`

固定 SQL 输出字段：

- `gene_variant_id`
- `gene`
- `variant`
- `ori_variant`
- `cosmic='.'`
- `mutFreq='.'`

这些字段只是知识库定义，还没有“是否发生”的判断结果。`JudgeComplex` 判中后才进 `drug_var_list`。

## 5.2 第二阶段：`update_cr_info` 补充字段

作用对象：

- 仅胚系位点 `crAllList`

调用：

```java
update_cr_info(map, user, lang);
```

补充字段：

- `check_date`：转换成人类可读的“X天前/未审核”
- `mutDesc`：`translateUtil.translate2(Gene, ori_variant, Zygosity)`
- `rpCr`
  - 若本地 `rp_cr` 无记录：构造只含 `GeneDesc`、`vardesc` 的 Map
  - 若有记录：查 `rp_cr` 现有记录，必要时更新 `GeneDesc`

SQL：

```sql
SELECT ... FROM nkb_gene_annotation_evw / gene description 相关视图
```

以及：

```sql
update rp_cr
set GeneDesc=#{gene_desc}, updated_by=#{user}, update_time=sysdate(), check_date=null
where record_id=#{record_id}
```

## 6. 共突变匹配逻辑

## 6.1 启动条件

- 癌种父子级包含 `9256`（肠癌）

## 6.2 知识库来源

`Complex` 定义来自：

```sql
select gene_variant_id,
       gene_symbol as gene,
       gene_variant as variant,
       ori_variant,
       '.' as cosmic,
       '.' as mutFreq
from nkb.gene_variant_evw
WHERE gene_symbol = 'Complex'
  and checking_status != 'Obsolete'
  and gene_variant_id IN (...)
```

## 6.3 模板差异

- 多靶点模板：只加载 `8337`
- 其他模板：加载 `8337, 9245, 12786`

## 6.4 Panel 基因覆盖限制

对每个共突变表达式，要求表达式里的基因必须都在当前 panel 检测范围内：

调用：

```java
List<String> panel_genes = analysisReportDao.getPanelGenesByReportID(report_id);
if (!panel_contains(variant, panel_genes)) continue;
```

## 6.5 发生判定

`JudgeComplex` 内部支持的表达式类型：

- `WildType`
- `ExonX Mutation`
- `ExonX Insertion Mutation`
- `ExonX Deletion Mutation`
- `ExonX InDel Mutation`
- `Fusion`
- `Amplification`
- `Deletion`
- 简单点位
- `${pathway}` 路径基因占位符

辅助方法：

- `wildType_happen`
- `mutation_happen`
- `exon_mutation_happen`
- `fusion_happen`
- `amplification_happen`
- `deletion_happen`
- `simple_mut_happen`

## 6.6 父级突变支持

若某个简单变异本身不等于目标 `variant`，但其 `parent_variant` 包含目标，也算命中：

```java
List<String> parentVariantList = (List<String>) map.get("parent_variant");
if (parentVariant.equals(variant)) { ... }
```

父级突变来源：

```sql
analysisReportDao.getParentVariant(gene_symbol, gene_variant)
```

失活兜底：

- 若没有父级突变，且 `variant` 含 `fs/*/+/−` 且不是 Fusion
- 再尝试把它归到 `Inactive Mutation`

## 7. 本地库与知识库优先级

优先级判断发生在 `handleDrugList` 中：

## 7.1 本地库相关对象

- `rp_var_drug_en7`
- `rp_unknown_var`
- `rp_drug_info`
- `rp_clinical_trial`
- `rp_cr`

## 7.2 知识库相关对象

- `nkb_var_drug_anno_view`
- `nkb.variant_drug_annotation`
- `nkb.variant_drug_anno_trial`
- `nkb.clinical_trial`
- `nkb.clinical_trial_exclude_disease`
- `nkb.approved_drug`
- `nkb.guideline_drug_evw`
- `nkb.guideline_drug_resistant`
- `nkb.gene_annotation`
- `nkb.variant_annotation`
- `nkb_variant_desc_evw`

## 7.3 优先级规则

步骤：

1. 先查本地 `rp_var_drug_en7`
2. 再查本地 `rp_unknown_var`
3. 计算本地更新时间 `reportVarDrugUpdateTime`
4. 计算知识库综合更新时间 `nkbUpdateTime`
5. 比较：

```java
if (reportVarDrugUpdateTime.before(nkbUpdateTime) || Flag != 0) {
    // 知识库新
    fetchNkbDrugInfo(...)
} else {
    // 本地库新
    fetchLocalDrugInfo(...)
}
```

## 7.4 本地更新时间的组成

- 来自 `rp_var_drug_en7.update_date`
- 若 `rp_unknown_var.update_date` 更晚，则覆盖为更晚时间

## 7.5 知识库更新时间的组成

由 `getNkbUpdateTime(...)` 聚合：

- `getVarDrugAnnoUpdateTime(...)`
- `getGeneAnnoUpdateTime(...)`
- `getVariantDescriptionUpdateTime(...)`
- `getVariantAnnoUpdateTime(...)`
- `getGeneDescriptionUpdateTime(...)`

对应 SQL 例子：

```sql
SELECT MAX(
  GREATEST(
    COALESCE(a.update_date, '1000-01-01 00:00:00'),
    COALESCE(t.update_date, '1000-01-01 00:00:00'),
    COALESCE(c.update_date, '1000-01-01 00:00:00'),
    COALESCE(d.update_date, '1000-01-01 00:00:00'),
    COALESCE(g.update_date, '1000-01-01 00:00:00'),
    COALESCE(p.update_date, '1000-01-01 00:00:00')
  )
) AS max_update_time
FROM ...
```

解释：

- 不只是“药物关联表更新时间”
- 还包含：
  - 药物注释
  - 变异说明
  - 基因说明
  - 临床试验
  - 相关药物信息

## 7.6 强制走知识库

只要 `Flag != 0` 就强制走知识库分支。

调用场景：

- `getAnalysisOfImmuneTestResults` 里对 TMB/MSI/HRD 虚拟位点会传 `Flag=1`

## 8. `handleDrugList` 详细逻辑

## 8.1 读取入参与基础字段

从 `Map a` 读取：

- `gene`
- `variant`
- `ori_variant`
- `cosmic`
- `mutFreq`
- `parent_mutID`

## 8.2 获取 mutationId 与 mutationIdList

调用：

```java
Integer mutationId = getMutationID(gene, variant);
List<Integer> mutationIdList = getMutIdList(mutationId);
```

### 8.2.1 `getMutationID` 规则

先查：

```sql
analysisReportDao.getMutationId(gene, variant)
```

特殊兼容：

- 变异名可能被替换成特殊标准名，如：
  - `KDD Mutation`
  - `Inactive Mutation`

### 8.2.2 `getMutIdList` 规则

- 包含当前 `mutationId`
- 再追加所有父级 mutationId：

```sql
analysisReportDao.getParentMutationId(mutationId)
```

### 8.2.3 本地父 mutID 补充

若当前记录或前端参数中带 `parent_mutID`，则把这些本地保存的父级 mutId 也追加进 `mutationIdList`

目的：

- 知识库还没更新，但人工先在本地修正了靶向关联

## 8.3 性别过滤

```java
String gender = lifeService.getGender(report_id);
List<Integer> sonIdList = complexMutationService.solidTumorFiltration(gender, diseaseIdList);
```

效果：

- 男性不输出女性生殖器官肿瘤及子级
- 女性不输出男性生殖器官肿瘤及子级
- 实体瘤不输出血液肿瘤及子级
- 血液肿瘤不输出实体瘤及子级

这会影响：

- `getOtherADrugListByIdList`
- `matchNKBVarDrug`
- 临床试验 / 其他癌种药物匹配范围

## 8.4 本地有药记录 / 本地未知记录

## 8.5 `InNKB` 与 `mapped_variant_id`

逻辑：

- 若 `mutationId != null`
  - `a.put("InNKB","true")`
  - `a.put("mapped_variant_id", mutationId)`
- 否则
  - `a.put("InNKB","false")`

## 8.6 位点说明 `mutDesc` / `variantDescription`

`mutDesc2`：

```java
String mutDesc = translateUtil.translate2(gene, ori_variant, mutFreq);
a.put("mutDesc2", mutDesc);
```

`variantDescription` 来源：

- 知识库新时：
  - `analysisReportDao.getVariantDescription(mutationIdList, lang)`
  - 若 `reportVarDrug.record_id == null` 且知识库没描述，回退默认说明
- 本地库新时：
  - 从 `varDrugNote` JSON 的第 3 段读取“突变说明”
- 未知临床意义时：
  - 仍可能使用 `getVariantDescription` 或默认说明

最终：

- `a.put("mutDesc", mutDesc + variantDescription)`
- `a.put("variantDescription", variantDescription)`

默认说明 `unvariantDescription` 规则：

- `Amplification` → “该变异为基因扩增...”
- `Loss` → “该变异为基因缺失...”
- `fs/*/+/-` 非 Fusion → “该变异为失活突变...”
- 其他 → “该突变临床意义未明...”

## 10. 药物等级分类规则

等级由 `getDrugLevel(Map b, List<Integer> parentdiseaseIdList)` 计算。

## 10.1 总体定义

源码注释：

- `1-4`：获益 `A/B/C/D`
- `5-8`：耐药 `A/B/C/D`
- `9`：其他/无效

## 10.2 依据字段

核心字段：

- `relationship`
  - `Resistant` 表示耐药
- `evidence_phase_id`

## 10.3 获益药物等级

规则：

- `evidence_phase_id > 22` → `1`
- `18 ~ 22` → `2`
- `16 ~ 17` → `3`
- `14`
  - `getGive == 2` → `3`
  - `getGive == 1` → `4`
  - 其他 → `9`
- `12 ~ 13` → `4`
- 其他 → `9`

## 10.4 耐药药物等级

前提：

- `relationship == Resistant`
- 且 `evidence_phase_id >= 12`

规则：

- `evidence_phase_id > 22` → `5`
- `18 ~ 22` → `6`
- `16 ~ 17` → `7`
- `14`
  - `getGive == 2` → `7`
  - `getGive == 1` → `8`
  - 其他 → `9`
- `12 ~ 13` → `8`
- 其他 → `9`

## 10.5 `getGive` 规则（仅 evidence_phase_id=14）

逻辑：

1. 调 `getClinicalNumber(annotation_id, parentdiseaseIdList)`
2. 若 `clinical_num > 0` → 返回 `"2"`
3. 否则若 `has_previous_clinical_result == null` 或 `"Y"` → 返回 `"1"`
4. 否则返回 `"0"`

这会影响：

- 获益：C or D
- 耐药：C or D

## 10.6 等级字符串的存储位置

不会直接存 `A/B/C/D` 字母，而是先存数字 `approve_range`

后续拆分：

- `1` → `drugsA`
- `2` → `drugsB`
- `3` → `drugsC`
- `4` → `drugsD`
- `5` → `resistant_drugsA`
- `6` → `resistant_drugsB`
- `7` → `resistant_drugsC`
- `8` → `resistant_drugsD`

## 12. `varDrugNote` 的组成与优先级

`varDrugNote` 是一个 JSON 字符串，来源于：

- 知识库分支：由 `getVarDrugNote(...)` 动态生成，再写入 `reportVarDrug.var_drug_desc`
- 本地分支：直接使用 `reportVarDrug.getVar_drug_desc()`

后续用途：

- 体细胞变异结果解析
- 未知临床意义解析
- `PotentialInformation`
- 预览页面药物说明

在代码中它至少会被拆出这些块：

- `突变说明:`
- `位点说明:`
- `用药说明:`
- `耐药说明:`
- `NCCN指南:`

优先级：

- 若知识库更新时间更新，重新生成新的 `varDrugNote`
- 若本地库更新时间更新，则保留本地 `varDrugNote`

## 15. `orderNum` 排序规则

由 `setOrderNum(a)` 生成，用于预览/生成报告时的位点顺序。

## 15.1 基础分

- 默认从 `mutFreq` 转成数值
- `mutFreq` 为空、`.`、含 `合`、含 `H` 时不加基础分
- 末尾 `X` 会先去掉再取数值

## 15.2 大类优先级

- CR 有药：`+90000`
- 靶向药物：
  - 共突变 `Complex`：`+50000`
  - 其他靶向药物：`+70000`
    - Amplification / Loss / Deletion 再 `+300`
    - Fusion 再 `+200`
- 非靶向药物：`+10000`

## 15.3 COSMIC 加分

- `cosmic != "."` → `+100`

## 15.4 药物等级加分

取 `drugList` 中每个药物 `approve_range` 对应：

- `1 -> 9000`
- `2 -> 8000`
- `3 -> 7000`
- `4 -> 6000`
- `5 -> 5000`
- `6 -> 4000`
- `7 -> 3000`
- `8 -> 2000`
- `9 -> 1000`

最终取最大值叠加。

## 16. 关键逻辑结论

1. `matchComplexMutation` 负责把“可能要参与用药判断的位点”收进 `drug_var_list`，但真正的药物匹配是在 `handleDrugList` 完成的。
2. `drug_var_list` 里既可能是体系位点，也可能是胚系位点、共突变、特殊肺癌共突变、甚至 HRD 虚拟位点。
3. 本地库和知识库的优先级不是固定“知识库优先”，而是**按更新时间比较**：
   - `rp_var_drug_en7` / `rp_unknown_var` 更新时间晚于知识库 → 本地优先
   - 知识库综合更新时间更晚 → 知识库优先并覆盖本地
4. 药物等级最终靠 `approve_range` 数字表达，`1-4` 是获益 A-D，`5-8` 是耐药 A-D，`9` 是无效/丢弃。
5. `getvusLevel()` 目前恒返回 `2`，导致“不报告”逻辑基本不会进入，是个明显的历史遗留点。
6. 本地库中的 `parent_mutID` 能反向影响知识库映射范围，这是“人工先修靶、知识库后更新”的兼容逻辑。
7. `varDrugNote` 是串联报告解析、潜在药物、临床试验描述的核心中间产物，应视为高价值字段。
